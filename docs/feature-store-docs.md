# Feature Store and Modeling Data Documentation - Tricura ML Case

This document describes the point-in-time feature artifacts used by the
incident-risk modeling pipeline, the target labels attached to the processed
model matrices, and the temporal validation strategy used in practice.

## Artifact Layout

The feature engineering pipeline writes two kinds of parquet artifacts:

- target-free feature stores under `data/feature_store`
- model-ready matrices under `data/processed`

| Artifact | Path | Rows | Columns | Contents |
|---|---|---:|---:|---|
| 7-day feature store | `data/feature_store/features_7d.parquet` | 66,312 | 228 | 5 meta columns + 223 features, no targets |
| 7-day model matrix | `data/processed/model_matrix_7d.parquet` | 66,312 | 230 | 5 meta columns + `fall_7d`, `rth_7d` + 223 features |
| 14-day feature store | `data/feature_store/features_14d.parquet` | 32,361 | 228 | 5 meta columns + 223 features, no targets |
| 14-day model matrix | `data/processed/model_matrix_14d.parquet` | 32,361 | 229 | 5 meta columns + `wound_14d` + 223 features |

These files are generated by:

- `feature_engineering/build_falls_rth_matrix.py`
- `feature_engineering/build_wound_matrix.py`

`modeling/train_models.py` reads the processed model matrices from
`data/processed`. New-batch scoring uses target-free features generated by
`feature_engineering/build_scoring_features.py`.

## Temporal Design

The modeling unit is a resident-window: one resident scored at a specific
`window_start`.

Both historical feature pipelines use the same feature logic and raw sources,
with different label horizons:

- Signal window: July 2023 through January 2025 labels
- Embargo: features only use data with timestamps `<= feature_cutoff`
- Feature cutoff: `window_start - 1 day`
- 7-day pipeline: non-overlapping 7-day windows, targets `fall_7d` and `rth_7d`
- 14-day pipeline: non-overlapping 14-day windows, target `wound_14d`

Conceptually:

```text
[feature lookback] -> feature_cutoff -> window_start -> label window
```

The one-day embargo is meant to protect against data-entry lag and accidental
same-day leakage.

## Observation Spine

The saved feature-store and processed artifacts share the same 5 meta columns:

| Column | Type | Description |
|---|---|---|
| `resident_id` | String | Resident identifier |
| `facility_id` | String | Facility identifier |
| `window_start` | Datetime | Start of the prediction window |
| `window_end` | Datetime | End of the prediction window |
| `feature_cutoff` | Datetime | Last allowed timestamp for feature data |

These columns define the row identity and temporal frame. They are not model
features and are excluded from `feature_cols` during training.

The parquet artifacts do not store a `split` column. Split boundaries are
applied later inside the modeling scripts.

| `rth_7d` | Int8 (0/1) | 0.8128% | Any unplanned hospital transfer with `effective_date` in `[window_start, window_end)` |

14-day processed matrix:

| Column | Type | Positive rate | Definition |
|---|---|---:|---|
| `wound_14d` | Int8 (0/1) | 1.3071% | Any `Wound` incident with `occurred_at` in `[window_start, window_end)` |

RTH labels use unplanned transfers only:

```text
planned_flag = False OR planned_flag IS NULL
```

## Hospital Admission Context

The admission feature block is implemented in
`feature_engineering/admission_features.py` and is joined into both the 7-day
and 14-day matrices.

It treats `hospital_admissions` as SNF admission/status context, not as the RTH
event table. The RTH target and RTH history continue to come from
`hospital_transfers`.

The 12 admission-context features are:

| Feature | Type | Meaning |
|---|---|---|
| `admission_active_count` | Int32 | Active admission rows at `feature_cutoff` |
| `admission_active_any` | Int8 | Any active admission row |
| `admission_active_post_acute` | Int8 | Any active `Post Acute` admission row |
| `admission_active_chronic_long_term` | Int8 | Any active `Chronic Long-Term` admission row |
| `admission_count_30d` | Int32 | Admission effective dates in prior 30 days |
| `admission_count_90d` | Int32 | Admission effective dates in prior 90 days |
| `admission_post_acute_30d` | Int32 | `Post Acute` effective dates in prior 30 days |
| `admission_post_acute_90d` | Int32 | `Post Acute` effective dates in prior 90 days |
| `admission_chronic_long_term_30d` | Int32 | `Chronic Long-Term` effective dates in prior 30 days |
| `admission_chronic_long_term_90d` | Int32 | `Chronic Long-Term` effective dates in prior 90 days |
| `admission_hospital_stay_to_30d` | Int32 | Known hospital-stay end dates in prior 30 days |
| `admission_hospital_stay_to_90d` | Int32 | Known hospital-stay end dates in prior 90 days |

Leakage controls:

- admission rows are eligible only when `effective_date <= feature_cutoff`
- admission rows are eligible only when `created_at <= feature_cutoff`
- active admission rows require `ineffective_date IS NULL OR ineffective_date > feature_cutoff`
- `hospital_stay_to` counts require `hospital_stay_to <= feature_cutoff`

This prevents late-entered admission rows or future hospital-stay dates from
entering earlier observation windows.

## Modeling Strategy in Practice

The feature store supports a tiered risk-scoring system, but the matrices in
this document are the Tier 1 supervised ML inputs:

| Target | Horizon | Model |
|---|---:|---|
| `fall_7d` | 7 days | CatBoost binary classifier |
| `rth_7d` | 7 days | CatBoost binary classifier |
| `wound_14d` | 14 days | CatBoost binary classifier |

CatBoost is used because the matrices contain meaningful missingness,
especially in vitals statistic columns, and CatBoost can consume missing values
without pre-imputation or feature scaling.

The practical training workflow in `modeling/train_models.py` is:

1. Load the processed model matrix for the target.
2. Exclude the 5 meta columns and all target columns from `feature_cols`.
3. Run expanding-window temporal cross-validation on pre-holdout data.
4. Optionally run Optuna tuning to minimize cross-validated log loss.
5. Generate leakage-safe calibration data from purged expanding-window
   out-of-fold predictions.
6. Fit an isotonic calibrator on those temporal out-of-fold predictions.
7. Train a final CatBoost model on all eligible pre-holdout rows.
8. Evaluate on the January 2025 holdout.
9. Log uncalibrated and calibrated model variants to MLflow.

The calibrated variant wraps the final CatBoost model with an isotonic
calibrator. The calibrator is fitted only on predictions from folds where the
fold model was trained on labels fully known before that fold boundary.

## Temporal Validation and Holdout Split

The current modeling code no longer uses a stored train/test/holdout split or a
fixed mid-2024 test set. Instead, it uses expanding-window validation and a
final January 2025 holdout.

Constants in `modeling/train_models.py`:

| Setting | Value |
|---|---:|
| Minimum initial training history | 26 weeks |
| Fold step | 4 weeks |
| Holdout start | `2025-01-01` |

For each CV fold boundary `b`:

```text
train: window_end <= b
test:  b <= window_start < b + horizon
```

The `window_end <= b` rule is a purge. It prevents a training row from having a
label window that overlaps the validation period.

Here `b` is the simulated scoring date for one validation fold: the model is
trained only on outcomes that would already be fully known by that date, then
tested on the next prediction window. The `fold_step` moves this simulated
scoring date forward every 4 weeks, so validation is repeated roughly monthly.

For example, for a 7-day target with `b = 2024-07-13`:

```text
train: window_end <= 2024-07-13
test:  2024-07-13 <= window_start < 2024-07-20
```

A row with `window_start = 2024-07-01` and `window_end = 2024-07-08` can be used
for training. A row with `window_start = 2024-07-10` and
`window_end = 2024-07-17` is excluded from training because its label window
would still be in progress on `2024-07-13`. The next fold would advance `b` by
4 weeks to `2024-08-10`. For the 14-day wound target, the same boundary logic is
used, but the test window is 14 days wide.

For final holdout evaluation:

```text
train:   window_end <= 2025-01-01
holdout: window_start >= 2025-01-01
```

Rows whose label window crosses the holdout boundary are excluded from final
training. This is why the final training row count plus holdout row count is
slightly smaller than the full matrix row count.

Current final train/holdout counts:

| Matrix | Split | Rows | Residents | Positive rate |
|---|---|---:|---:|---|
| 7-day | Final train | 61,679 | 2,614 | `fall_7d`: 2.3865%, `rth_7d`: 0.8155% |
| 7-day | Holdout | 3,612 | 1,007 | `fall_7d`: 2.9070%, `rth_7d`: 0.8029% |
| 14-day | Final train | 30,243 | 2,256 | `wound_14d`: 1.3160% |

## Production Scoring Features

For new-batch scoring, `feature_engineering/build_scoring_features.py` builds a
target-free feature row for each active resident at an `as_of_date`.

The scoring artifact keeps the same 5 meta columns and 223 feature columns as
the historical 7-day feature store:

```text
window_start   = as_of_date
window_end     = as_of_date + 7 days
feature_cutoff = as_of_date - 1 day
```

`modeling/score_composite.py` then loads MLflow models, aligns the scoring
features to each model's training feature schema, and produces model
probabilities for the composite risk score.

## Null Handling

- Vitals statistic columns preserve nulls when no measurement exists in the lookback window.
- Vitals monitoring flags are explicit `0/1` indicators and never null.
- Diagnosis flags may be null when a resident has no diagnosis records at all.
- History, admission-context, needs, labs, and document-tag features are filled with `0` when no matching prior records exist.
- Downstream CatBoost models consume missing values directly from the processed matrices.
