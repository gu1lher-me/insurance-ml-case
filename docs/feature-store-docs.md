# Feature Store Documentation - Tricura ML Case

This document describes the parquet artifacts produced by the refactored feature engineering pipeline.

## Artifact Layout

The pipeline now separates target-free features from model-ready matrices:

| Artifact | Path | Rows | Columns | Contents |
|---|---|---|---|---|
| 7-day feature store | `data/feature_store/features_7d.parquet` | 66,312 | 228 | 5 meta columns + 223 features, no targets |
| 7-day model matrix | `data/processed/model_matrix_7d.parquet` | 66,312 | 230 | 5 meta columns + `fall_7d`, `rth_7d` + 223 features |
| 14-day feature store | `data/feature_store/features_14d.parquet` | 32,361 | 228 | 5 meta columns + 223 features, no targets |
| 14-day model matrix | `data/processed/model_matrix_14d.parquet` | 32,361 | 229 | 5 meta columns + `wound_14d` + 223 features |

These files are generated by:

- `feature_engineering/build_falls_rth_matrix.py`
- `feature_engineering/build_wound_matrix.py`

`modeling/train_models.py` reads the processed model matrices from `data/processed`.

## Temporal Design

Both pipelines use the same feature logic and raw sources, with different label horizons:

- Signal window: July 2023 to February 2025
- Embargo: features only use data with timestamps `<= feature_cutoff`
- Feature cutoff: `window_start - 1 day`
- 7-day pipeline: non-overlapping 7-day windows, targets `fall_7d` and `rth_7d`
- 14-day pipeline: non-overlapping 14-day windows, target `wound_14d`

Conceptually:

```text
[feature lookback] -> feature_cutoff -> window_start -> label window
```

## Observation Spine

The saved feature-store and processed artifacts share the same meta columns:

| Column | Type | Description |
|---|---|---|
| `resident_id` | String | Resident identifier |
| `facility_id` | String | Facility identifier |
| `window_start` | Datetime | Start of the prediction window |
| `window_end` | Datetime | End of the prediction window |
| `feature_cutoff` | Datetime | Last allowed timestamp for feature data |

The parquet artifacts do not store a `split` column. Train/test/holdout boundaries are applied later inside `modeling/train_models.py`.

## Target Labels

7-day processed matrix:

| Column | Type | Positive rate | Definition |
|---|---|---|---|
| `fall_7d` | Int8 (0/1) | 2.4204% | Any `Fall` incident with `occurred_at` in `[window_start, window_end)` |
| `rth_7d` | Int8 (0/1) | 0.8128% | Any unplanned hospital transfer with `effective_date` in `[window_start, window_end)` |

14-day processed matrix:

| Column | Type | Positive rate | Definition |
|---|---|---|---|
| `wound_14d` | Int8 (0/1) | 1.3071% | Any `Wound` incident with `occurred_at` in `[window_start, window_end)` |

RTH uses unplanned transfers only:

- `planned_flag = False OR planned_flag IS NULL`

## Feature Set

Both horizons use the same 223 engineered features. The feature-store artifacts contain exactly these features plus the 5 meta columns above.

| Group | Count | Notes |
|---|---|---|
| Demographics | 2 | Age at window, length of stay |
| Vitals rolling statistics | 120 | 8 vital types x 3 lookbacks x 5 stats |
| Vitals monitoring flags | 24 | Binary "measured in window" indicators |
| Diagnoses | 21 | Active diagnosis counts, chapter counts, fall-risk and RTH-risk flags |
| Incident history | 13 | Prior counts by incident type and lookback |
| RTH history | 4 | Prior unplanned transfer counts |
| Hospital admission context | 12 | Active/recent SNF admission status and recent hospital-stay context |
| Care plan needs | 5 | Open need counts by category |
| Lab reports | 6 | Abnormal, critical, and total counts for 14d and 30d windows |
| Document tags | 16 | Binary NLP-derived clinical tag flags |

Raw inputs used by both pipelines:

- `residents`
- `vitals`
- `incidents`
- `diagnoses`
- `hospital_transfers`
- `hospital_admissions`
- `needs`
- `lab_reports`
- `document_tags`

Hospital admission features use only rows where both
`effective_date <= feature_cutoff` and `created_at <= feature_cutoff`.
Recent `hospital_stay_to` counts also require
`hospital_stay_to <= feature_cutoff`, preventing late-entered admission rows or
future hospital-stay dates from entering earlier observation windows.

## Modeling Split

Temporal split logic is a modeling concern, not a stored feature-store field.

For the 7-day modeling pipeline, the current split is:

| Split | Windows | Residents | fall_7d rate | rth_7d rate |
|---|---|---|---|---|
| `train` | 38,389 | 1,749 | 2.25% | 0.72% |
| `test` | 24,311 | 1,712 | 2.62% | 0.95% |
| `holdout` | 3,612 | 1,007 | 2.91% | 0.80% |

Boundaries:

- Train: `window_start < 2024-07-01`
- Test: `2024-07-01 <= window_start < 2025-01-01`
- Holdout: `window_start >= 2025-01-01`

## Null Handling

- Vitals statistic columns preserve nulls when no measurement exists in the lookback window.
- Vitals monitoring flags are explicit `0/1` indicators and never null.
- Diagnosis flags may be null when a resident has no diagnosis records at all.
- History, admission-context, needs, labs, and document-tag features are filled with `0` when no matching prior records exist.
- Downstream modeling uses CatBoost, which can consume missing values directly from the processed matrices.

## Excluded Tables

The following raw tables are still excluded from the feature set because coverage is too sparse for this proof of concept:

| Table | Resident coverage | Reason excluded |
|---|---|---|
| `medications` | 16% | Partial facility rollout |
| `adl_responses` | 3.2% | Sparse coverage and short overlap with signal window |
| `gg_responses` | 4.5% | Too sparse for population-level features |
| `therapy_tracks` | 7.3% | Insufficient coverage for reliable signal |
